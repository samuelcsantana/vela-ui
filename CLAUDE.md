# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Vela UI is the frontend half of **Vela**, a multi-tenant SaaS portfolio project. The explicit goal is to make the multi-tenancy story *visible*: RBAC-driven dashboards (a `VELA_ADMIN` sees the whole platform, a tenant `ADMIN`/`MEMBER` only their own company), white-label theming per tenant, and defensive UX around destructive operations. Demo data and UI copy are recruiter-visible — keep them professional, and add both pt/en translations for any new user-facing string.

The backend is the sibling repo **vela-core** (Fastify + Prisma, deployed on Render). This app deploys on Vercel at https://vela-ui-drab.vercel.app. `swagger.json` at the repo root is a checked-in snapshot of vela-core's OpenAPI spec, kept for reference — refresh it from `GET /docs/json` when endpoints change; never hand-edit it.

There is no server side to this app — it's a pure SPA (React 19 + Rsbuild/Rspack, not Vite, not Next).

## Commands

```bash
npm run dev            # dev server at http://localhost:3011 (fixed port, see rsbuild.config.ts)
npm run build           # production build
npm run preview         # preview the production build locally

npm run lint             # eslint . (typescript-eslint typeChecked + react-hooks + jsx-a11y) — must be zero errors
npm run typecheck        # tsc --noEmit — must be zero errors

npm run test             # vitest, watch mode
npm run test:coverage    # vitest run --coverage — fails below 100% (see thresholds below)
npx vitest run path/to/File.test.tsx        # single test file
npx vitest run -t "test name substring"     # single test by name

npm run test:e2e                             # playwright test (all e2e specs)
npx playwright test e2e/some-flow.spec.ts    # single e2e spec
```

Environment: copy `.env.example` to `.env` and set `VITE_API_URL` (e.g. `http://localhost:3010/api`, matching vela-core's default port). Rsbuild inlines `VITE_`-prefixed vars into the static bundle at build time (same as Vite) — there is no runtime env for the Nginx-served production build. Docker: `docker compose up -d --build` serves the production build via Nginx on `3011`; the compose file intentionally has no `api` service since vela-core lives in its own repo with its own compose stack — run both side by side for full-stack local dev.

Never bypass the pre-commit hook with `--no-verify` — husky + lint-staged run secretlint on every commit.

## Testing notes

- Vitest + `jsdom` + Testing Library (`@testing-library/react`, `jest-dom`, `user-event`). Setup file: `src/test/setup.ts`.
- Coverage thresholds are enforced in `vitest.config.ts` (currently ~99.9% statements/lines, 97% branches, 99.4% functions) — write the test in the same change that adds a branch, not after. Config, generated files, and route files are excluded from coverage (see `vitest.config.ts`'s `coverage.exclude`).
- External boundaries are mocked per test file: TanStack Router, Zustand-backed stores, `react-i18next`, Recharts, Radix UI. i18n is *not* initialized in unit tests — components render raw translation keys, and tests assert on keys like `'tenants.form.title'` on purpose. Don't "fix" this by initializing i18next in tests.
- `src/routeTree.gen.ts` is generated by the TanStack Router plugin — never hand-edit it, never lint it.
- E2E (`e2e/`) drives the real app in Chromium and mocks every vela-core endpoint via `page.route()`, so it needs no backend/database and runs deterministically in CI. New e2e tests should stay self-contained the same way, with fixtures mirroring vela-core's real response shapes (see `e2e/helpers.ts`).

## Architecture

### Feature-sliced structure

```
src/
  components/     # Reusable, domain-agnostic UI: design system + app shell (layout, header, sidebar)
  components/ui/  # shadcn/ui primitives (Radix-based)
  hooks/          # Generic hooks shared across features (useDebounce, useMediaQuery, ...)
  lib/            # Infra: axios instance (api.ts), query-client, i18n setup, framework-agnostic utils
  features/       # Domain modules: auth, dashboard, tenants, users
                  #   each has its own {api,components,hooks,store,schema}
  store/          # Global/cross-feature Zustand stores (theme, layout)
  routes/         # TanStack Router file-based route definitions — thin, real logic lives in features/
```

**Dependency direction is enforced by convention, not tooling:** `components/` and `hooks/` never import from `features/`; `features/` may import from `components/`, `hooks/`, `lib/`, and `store/`. The one documented exception is `features/auth/store/auth-store.ts`, treated as global session state because the app shell (`AppLayout`, `Header`, `Sidebar`, route guards) depends on it to know who's logged in — layout components may import it directly despite physically living under `features/`. Don't replicate this exception for other features without an equivalent justification (a real dependency from the application shell).

### State separation

Two global state mechanisms only — no Redux, MobX, or equivalents:

- **Server state** (anything from an API) lives exclusively in TanStack Query (`useQuery`/`useMutation`) — never copied into Zustand or component state, to avoid cache duplication/staleness. Optimistic/instant updates go through the query cache (`setQueryData`) with invalidation on settle, not ad-hoc state syncing.
- **Client state** (sidebar open/closed, theme, session, wizard steps, row selection) lives in Zustand, split into small scoped stores rather than one monolith. Selectors must be granular (`useStore((s) => s.field)`), never `useStore((s) => s)`, to avoid cascading re-renders. Prefer a store/hook local to a feature; only promote to `store/` or `hooks/` on real (not speculative) reuse.

### API access

All API access goes through a feature's `api/` module using the shared Axios instance (`src/lib/api.ts`, `withCredentials: true` — auth is an httpOnly cookie, never a token in `localStorage`). Components never call axios directly; they consume TanStack Query hooks from the feature's `hooks/`. Keep fetch/mutation logic in `features/*` hooks, not in presentation components — prefer "dumb" data-in-via-props components.

### Multi-tenant & RBAC model

Every `User` and `Tenant` is scoped by `tenantId`; vela-core enforces the boundary server-side. **RBAC in the UI is presentational, never authoritative** — roles gate what renders (e.g. "Create Tenant"/"Delete Tenant" only for `VELA_ADMIN`) and route guards redirect early, but real enforcement is vela-core's query-level scoping. Never treat a hidden button as a security boundary.

| Role | Scope |
|---|---|
| `VELA_ADMIN` | Platform root — every tenant, every user, global metrics, tenant lifecycle (create/delete) |
| `ADMIN` | Their own tenant only — manage that tenant's users |
| `MEMBER` | Their own tenant, read-scoped |

Two literal cross-repo contracts with vela-core — changing either means changing both repos in the same milestone:
- `GET /metrics/dashboard` returns `scope: 'GLOBAL' | 'TENANT'`, and the dashboard switches on it.
- The `409 TENANT_HAS_USERS` error code drives the double-confirmation cascade-delete dialog when deleting a tenant that still has active users.

### Auth & routing

Routes are file-based under `src/routes/` (TanStack Router). Protected routes live under a pathless `_protected` layout route whose `beforeLoad` guard redirects unauthenticated visitors to `/login` and role-ineligible visitors back to the dashboard; the app shell (sidebar/header) only renders for authenticated routes. Auth guards use `throw redirect(...)` — that's the framework contract, which is why eslint's `only-throw-error` is disabled for `src/routes/**`.

### White-label theming

A tenant's `primaryColor` is applied at runtime via CSS custom properties (`use-tenant-branding` hook). `GET /tenants/:slug` is deliberately a public endpoint so branding can render before login (see `/$slug/login` route).

### Dialogs

Reuse `ConfirmDialog` / follow existing dialog components rather than inventing a new pattern. The established pattern: backdrop click closes via an `event.target === event.currentTarget` check on the `role="presentation"` overlay (no `stopPropagation` on the panel), `Escape` closes via a document keydown listener, and focus returns to the previously focused element on close.

### Responsive tables

`UsersTable`/`TenantsTable` declare explicit ARIA table roles (`scope`, `role="columnheader"/"rowheader"/"cell"`) because the mobile card layout (`display: block`) strips native table semantics. The file-level eslint-disable comments there are intentional — don't "clean them up".

### Accessibility

Treated as a first-class feature, not an afterthought: landmark elements, a skip-to-main-content link, full dialog focus traps + focus restoration, `Tab`-order-safe off-canvas sidebar (native `inert` attribute), `aria-live` regions for async states and form errors, `aria-invalid`/`aria-describedby` wired to every validated field. `@axe-core/react` runs in dev and logs violations to the console. New UI must keep `jsx-a11y` clean without blanket disables.

### i18n

`react-i18next` + `i18next-browser-languagedetector`, English/Portuguese. Translation keys live in `src/lib/i18n/`. Language resolution: saved choice (`localStorage`) → browser language → English fallback. Codebase language (always English — components, variables, comments, commit messages) and UI language are independent axes. Zod validation messages and formatted dates also follow the active language.

### Forms

Every form uses `react-hook-form` with a Zod schema resolved via `zodResolver`. Schemas live in `lib/schemas` or alongside the feature (`features/<feature>/schema.ts`) — the single source of truth for validation; don't duplicate validation rules manually. Types are inferred from schemas (`z.infer<typeof schema>`) rather than hand-declared where possible.

### Performance conventions

- Every routable feature is loaded via `React.lazy` + `Suspense` (the `*.lazy.tsx` route files in `src/routes/`).
- Configure `staleTime`/`gcTime` per query in `src/lib/query-client.ts` usage when data doesn't change on every request; avoid aggressive refetching without reason.

## Version control

Gitflow: `main` (production, auto-deployed by Vercel) ← `develop` (integration) ← `feature/*` / `bugfix/*` / `chore/*`. Never commit directly to `main`. Conventional Commits in English (`feat(ui):`, `fix(ui):`, `chore(ui):`, `docs:`, `test:`); each PR is one atomic change, squash-merged with a clean final message.

## CI/CD

Every push/PR to `main` or `develop` runs three GitHub Actions workflows:
- `ci.yml` — lint, typecheck, production build.
- `security.yml` — `npm audit --audit-level=high` + a secretlint sweep (also weekly cron).
- `tests.yml` — `test:coverage` (gate, not report — fails below threshold) + Playwright e2e, then uploads lcov to Codecov.

`vercel.json` has a rewrite rule so client-side routes resolve on refresh/deep-link instead of 404ing.
